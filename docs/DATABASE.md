# 🗄️ Database Design

This document describes the database schema used by Cloud-Sentinel and how audit reports are stored.

---

# Overview

Cloud-Sentinel uses **PostgreSQL** as its primary database.

The database stores:

* User accounts
* Audit reports
* Audit metadata

PostgreSQL was chosen because it provides:

* ACID-compliant transactions
* Excellent JSON support (JSONB)
* High reliability
* Strong indexing and query capabilities

---

# Database Schema

## audit_reports

Stores the results of completed AWS security audits.

| Column     | Type        | Description                       |
| ---------- | ----------- | ---------------------------------- |
| id         | SERIAL      | Primary key                        |
| user_id    | INTEGER     | User who initiated the audit (FK, cascades on delete) |
| report     | JSONB       | Complete audit report (includes `task_id` inside the JSON) |
| created_at | TIMESTAMPTZ | Audit completion timestamp         |

Note: `task_id` lives inside the `report` JSONB payload, not as its own
column on this table - see `audit_tasks` below for the queryable version
used for status tracking.

## audit_tasks

Tracks the lifecycle of a queued audit so the dashboard can report real
progress instead of polling `audit_reports` and hoping something new shows up.

| Column     | Type        | Description                                   |
| ---------- | ----------- | ---------------------------------------------- |
| task_id    | TEXT        | Primary key, generated by the gateway (UUID)   |
| user_id    | INTEGER     | User who initiated the audit (FK, cascades on delete) |
| status     | TEXT        | `queued` \| `running` \| `done` \| `error`      |
| mode       | TEXT        | `aws` or `floci`                                |
| report_id  | INTEGER     | FK to `audit_reports.id` once the audit completes (nullable) |
| error      | TEXT        | Final error message if `status = 'error'` (nullable) |
| created_at | TIMESTAMPTZ | When the audit was queued                       |
| updated_at | TIMESTAMPTZ | Last status change                              |

The worker retries failed tasks (`MAX_TASK_RETRIES`, default 3, with a
`TASK_RETRY_DELAY_SECONDS` delay between attempts) before settling on a final
`error` status, so `status` can go back to `running` mid-retry. Tasks that
exhaust their retries are also pushed onto the `audit_tasks_dead` Redis list
for manual inspection.

# Report Structure

Each report is stored as a JSON document.

Example:

```json id="o0ezj2"
{
  "findings": [
    {
      "type": "S3PublicAccess",
      "severity": "critical",
      "resource": "my-bucket",
      "details": "Bucket is publicly accessible"
    },
    {
      "type": "SecurityGroupOpen",
      "severity": "high",
      "resource": "sg-0123456789",
      "details": "Port 22 is open to the internet"
    }
  ]
}
```

Using **JSONB** allows the report structure to evolve without requiring database schema changes.

# Relationships

```text id="kdx47p"
Users
   │
   │ 1
   │
   ├──▶ Audit Reports
   │
   └──▶ Audit Tasks ──▶ Audit Reports (report_id, once complete)
```

Each user can own multiple audit reports and audit tasks. Deleting a user
cascades to both.

# Why JSONB?

Audit findings can vary depending on:

* AWS services scanned
* Number of resources
* Types of security issues

Using **JSONB** provides:

* Flexible storage
* Efficient querying
* No schema migrations when new finding types are introduced

# Example Queries

Retrieve all audit reports:

```sql id="9h2ajz"
SELECT *
FROM audit_reports
ORDER BY created_at DESC;
```

Retrieve reports for a specific user:

```sql id="uhggzc"
SELECT *
FROM audit_reports
WHERE user_id = 1
ORDER BY created_at DESC;
```

Retrieve the status of a specific audit task:

```sql id="wyqzq0"
SELECT status, report_id, error
FROM audit_tasks
WHERE task_id = 'abc123';
```

# Data Lifecycle

1. User starts an audit; the gateway generates a `task_id` and inserts a
   `queued` row into `audit_tasks`.
2. Gateway pushes the task onto the Redis `audit_tasks` queue.
3. Worker picks it up, marks it `running`, and executes AWS scans.
4. Worker generates a report and inserts it into `audit_reports`.
5. Worker marks the task `done` (or `error`, after retries, on failure).
6. Dashboard polls `GET /api/audit/:task_id` for status, then retrieves the
   finished report through `GET /api/reports`.

# Future Improvements

Potential enhancements include:

* Separate table for individual findings
* Report versioning
* Soft deletes
* Audit history
* Indexing on frequently queried JSON fields
* Retention policies for old reports
* Export reports to external storage

These improvements can be implemented without changing the overall architecture.
